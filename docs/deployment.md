# 上线与数据维护

## 推荐路径：托管网站

此版本是支持手机浏览器的网站。所有成员使用各自账号访问同一批企业与产品资料。先使用网站即可满足远程录入；小程序、原生 App 和应用商店发布不在本次交付中。

不必自己购买和维护一台云服务器，但持续运行的网站仍需要付费托管资源。本仓库提供 Render Blueprint：付费 Python Web Service + 10 GB 持久化磁盘 + 平台 HTTPS。费用由平台确认页列出，不会因本仓库的代码推送自动购买资源。

如果主要用户在中国大陆，上线前应实测目标网络的访问速度。也可以将同一 Flask/Gunicorn 服务部署到国内云；使用大陆服务器和自有域名时按服务商要求办理备案。不要用 GitHub Pages 托管本项目：它不能运行此 Python 后端及数据库。

## 首次部署

1. 注册并登录你自己的 Render 账号，连接本 GitHub 仓库。
2. 使用 README 中的部署链接或控制台创建 Blueprint，选择仓库 `andi-zhx/trade_agent` 的 `main` 分支。
3. 复核 `render.yaml` 创建的 **Starter Web Service、持久化磁盘** 和费用。不要改成临时文件系统的免费服务。
4. 在平台的安全环境变量设置中填写 `TRADE_ADMIN_PASSWORD`，至少 12 个字符。管理员默认用户名为 `admin`，可以在 `TRADE_ADMIN_USERNAME` 中设置。`TRADE_SECRET_KEY` 由平台随机生成，保留它以维持会话安全。不要把密码填到代码、聊天或 README。
5. 部署成功后使用平台提供的 HTTPS 地址登录。进入“成员管理”添加普通成员，再将网址及各自账号通过你的安全渠道交给他们。成员可自行修改密码。
6. 录入一条测试企业和产品，刷新页面确认资料仍在，上传并下载一个附件，生成完整备份并下载。在平台重启服务后，再确认资料和附件仍可用。
7. 确认独立备份存储与磁盘快照策略后再录入真实资料。需要自有域名时，在云平台绑定并按其说明配置 DNS；这不是首次使用的前提。

本次代码已经提供部署配置；尚未在你的云账号里创建或购买服务，也未获得公网网址。网站真正上线以目标平台部署、HTTPS 登录及重启后验证成功为准。

## 运行约定

| 配置 | 用途 |
| --- | --- |
| `TRADE_ENV=production` | 生产模式，禁用演示密码初始化 |
| `TRADE_DATA_DIR=/var/data` | 数据库、附件和备份必须位于持久化挂载中 |
| `TRADE_SECRET_KEY` | 至少 32 字符，平台生成的私密随机值 |
| `TRADE_ADMIN_USERNAME` | 首次管理员用户名，默认 `admin` |
| `TRADE_ADMIN_PASSWORD` | 首次创建或迁移默认管理员时使用，后续不覆盖已修改的密码 |
| `TRADE_TRUST_PROXY=1` | 仅在 Render 等单层可信 HTTPS 代理之后启用 |
| `PORT` | 平台分配的内部 HTTP 端口 |

启动命令：`gunicorn -c gunicorn.conf.py wsgi:app`。入口会初始化/兼容迁移数据库，然后启动后台备份线程。`/healthz` 查询数据库中的用户表，供平台探测。

界面新增页面的时间显示为北京时间，数据库仍使用 UTC。

固定 **1 worker、4 threads、1 个服务实例**。SQLite 使用 WAL 和 30 秒锁等待；Gunicorn 启动配置不要开启 preload，不要与另一个 `python app.py` 实例共用同一份库。后台任务每小时检查一次当天是否已备份，首次启动约 10 秒后检查，失败后约 5 分钟重试。

网站更新仅替换代码，数据目录保留。自动部署默认关闭：更新前先做完整备份、等待 CI 通过，再在平台手动部署新提交。新增的版本字段会自动迁移；首次升级旧库前会在 `backups/database/pre_upgrade_*.sqlite` 留下原始数据库快照。不得使用 `db.drop_all()` 或重新生成样例数据来升级生产库。

## 把原来单机版的资料迁上去

GitHub 只有源代码，**你原电脑上的 `trade_agent.db` 和 `uploads/` 不会自动上传到网站**。

1. 先停止原单机程序，完整复制原数据库和附件目录到另一处安全位置。不要删原件。
2. 在原电脑更新本版本、安装依赖。用 `python manage.py backup --output 你指定的新备份路径.zip` 生成完整资料包。该命令不启动 Web 服务。
3. 将完整资料包通过目标平台支持的安全文件传输方式放到持久化磁盘。不要通过公开 GitHub 仓库传输。
4. 在平台 Shell 中执行 `python manage.py restore /var/data/迁移资料.zip --to /var/data/imported`，目标目录必须不存在。
5. 将生产环境变量 `TRADE_DATA_DIR` 改为 `/var/data/imported`，保留原来的持久化磁盘挂载 `/var/data`。配置生产管理员密码并重新部署/重启。
6. 核对企业、产品数量、典型附件和成员登录。迁入的本地默认管理员密码会换成平台配置的密码，默认普通演示账号会停用；自定义账号和历史资料保留。
7. 在确认新网站资料正确、备份可恢复后，再决定何时停止使用原单机资料。不要两边继续编辑后直接覆盖数据库。

## 日常备份

管理员使用“生成完整资料包”即可，无需分别处理数据库与附件。完整包内有 SQLite 在线快照、`uploads/` 和 `manifest.json`（文件 SHA-256 校验）。SQLite 通过原生 backup API 生成一致快照，包括已提交但尚在 WAL 中的数据。

每天自动备份一份完整资料包，默认最多保留 30 份且不超过 30 天；同一天的手动备份也计入上限。下载的完整包需要定期另存到另一台设备/独立云存储。云平台自带磁盘快照是额外保护，不能代替资料包恢复演练。当前版本没有配置或验证异地自动上传，不要将“本机自动备份”理解为“异地备份”。

磁盘容量要包含附件和保留的备份副本；粗略预留当前资料体积的 32 倍（原件、30 份备份和生成新备份的临时空间）。默认 10 GB 适合起步，附件达到数百 MB 后应评估扩容。附件较多时及时扩容；监控平台磁盘使用率并保持充足空闲空间。磁盘不足时保存/备份可能失败，网站不能保证在磁盘故障下继续写入。不要在仍有写入时直接复制单个 `.db` 文件而遗漏 WAL。

## 从备份恢复

1. 通知成员暂停录入；先为当前资料另做一个完整备份。
2. 校验并恢复到一个新目录：

   ```bash
   python manage.py restore /var/data/完整资料包.zip --to /var/data/restored-2026
   ```

3. 工具会检查文件清单、路径、SHA-256、数据库完整性以及附件引用，任何一步失败都不切换现有资料。目标已存在时拒绝覆盖。
4. 停止 Web 服务或进入维护窗口，在平台将 `TRADE_DATA_DIR` 改到新目录，然后重启。新目录必须仍位于持久化挂载中。
5. 验证登录、企业/产品数量、附件下载和新备份；确认无误后恢复录入。保留恢复前的资料，不要立即删除。

老版本单独的数据库备份与附件 ZIP 没有 `manifest.json`，不能直接交给新恢复命令。应先在离线目录中恢复老版本 `.db` 与 `uploads/`，检查完整，再用新版本生成完整资料包。

## 已做与未做的验证

仓库自动化测试会验证业务保存、权限、CSRF、旧库迁移、编辑冲突、软删除恢复、备份校验和文件恢复。浏览器流程需要在目标平台上线后再验收一次，尤其是 HTTPS Cookie、反向代理、持久化磁盘和附件下载。

稳定性依赖托管平台、独立备份和实际恢复演练。日备份存在从上次成功备份至故障时刻的数据恢复窗口，不能承诺零丢失。这个版本适合小团队共享资料，不提供离线录入或多实例数据库同步。
